# AppWatcher beta移行前の信頼性改善計画

## 目的と基準

設定変更やメンテナンス操作による意図しない起動を防ぎ、ログ障害が監視を停止させない構成にする。信頼性の指摘8件を対象とし、UI高速化は別対応とする。

- リポジトリ：`C:\work\codex\projects\AppWatcher`
- 調査基準：`0b39118`／`0.1.0-alpha.20`
- ブランチ：`feature/initial-implementation`
- 調査時の検証：Releaseビルド警告0・エラー0、既存テスト15件成功、pre-betaチェック成功。
- 完了版は`0.1.0-alpha.21`。beta移行、push、タグ、公開、実運用への差し替えは行わない。
- 稼働中の監視対象、実設定・DB・タスク登録を変更しない。変更は日本語メッセージでコミットする。

時限メンテナンス解除の自己キャンセルと、手動Stop後のメンテナンス解除による起動は隔離したメモリ内検証で再現済み。他の指摘も回帰テストで条件を固定する。

## 1. 設定再読み込みで実行状態を保持する

`SupervisorEngine.ReloadAsync`をアプリID単位の差分適用へ変更する。

- 変更なし：既存監視を維持する。
- 追加：新しい対象だけを初期化する。
- 削除：監視解除だけを行い、実行中プロセスを残す。
- 通常の変更：手動Stop、Pause期限、Backoff期限、再起動履歴を保持する。
- 名前やログレベルの変更で起動・停止しない。引数・作業ディレクトリは次回起動から適用する。
- ハング設定変更時は旧ループをキャンセル・終了待ちしてから更新する。
- 監視無効化は自動処理を止めるが、実行中プロセスの追跡は維持する。
- `AttachExisting=false`でも追跡中の対象を捨てない。`StartWithWatcher`を再読み込み時の起動指示として扱わない。

実行ファイル・権限変更には明示的なStopを要求する。UIとホストの双方で検査し、実行中・復旧待機中には拒否する。権限移管先でも停止を保持し、Startを待つ。UIは移管先を旧設定で起動してから保存・再読み込みを行う。

候補全体を適用前に検証し、重複ID、不正な定義、適用不能な変更で既存監視を壊さない。

## 2. タイマーと停止意図を修正する

- ユーザーのStop意図と表示状態を分離し、Start／Restart以外ではStopを解除しない。
- Pause／Resume、メンテナンス解除、設定再読み込みでもStopを保持する。
- ホスト再起動をまたぐ永続Pauseは追加しない。
- 時限メンテナンスのタイマーキャンセルと、解除処理のキャンセルを分離する。
- 世代番号で古いPauseタイマー・再起動予約を無効化する。
- 再起動待機中は監視ロックを保持しない。待機後にStop、Pause、世代、シャットダウン、再起動ポリシーを確認する。
- Pause中に終了した対象は、Stopでなく、再起動ポリシーとBackoffが許す場合だけ復旧する。
- 終了イベントはプロセス参照を照合し、旧プロセスの通知で新しい状態を変更しない。
- 非同期処理を追跡し、破棄時はキャンセル後に終了を待つ。
- スナップショットは公開済みの不変値を使い、再起動履歴の読み取りではQueueを書き換えない。
- 子プロセスを終了しない。AppWatcher終了時は対象からDetachするだけとする。

## 3. トレイ・UI・IPCの動作を統一する

- 全体Pause／Resumeは通常Agentと管理者Helperの両方へ送信する。
- 共通処理で両ホストの応答を評価し、片側失敗を表示する。成功側を勝手に巻き戻さない。
- 管理者対象がなく、Helperも停止中なら不在をエラーにせず、操作のためだけに起動しない。
- 設定再読み込みの失敗・タイムアウトを無視せず、無条件の再送もしない。
- 再起動待機中・Backoff中にもStopを使えるようにする。
- 停止失敗時はPIDを残して失敗を表示し、自動再起動抑止は保持する。
- 既存IPCコマンド名と設定schemaは維持する。`ReloadConfiguration`には適用前検証用の任意`ConfigurationPreview`を追加する。

## 4. 設定保存をプロセス間で排他する

- 同一データディレクトリの`config.lock`を`FileShare.None`で開き、読込・初回作成・移行・バックアップ回転・保存を同じ排他区間に含める。
- 取得待ちは10秒、キャンセル可能。待機失敗を設定破損として扱わない。
- 一時ファイルは同一ディレクトリの一意名とし、自分のファイルだけを後処理する。
- 書込ハンドルを閉じてから、既存ファイルは置換、初回は移動で確定する。
- バックアップ3世代、新schema拒否、メモリ上の破損復旧を保持する。
- `ConfigService.UpdateAsync`で最新設定へ変更項目だけを反映する。
- 復旧後の保存で、破損した本体が正常バックアップを押し出さないようにする。

## 5. DB障害でも監視を開始・継続する

- 起動時のDB初期化を監視開始の必須条件にしない。
- ログI/Oを上限付きキューへ分離し、監視ロックで長時間待たない。
- キュー上限は1024件。満杯時は超過件数をfallbackへ記録し、無制限にメモリを消費しない。
- DB障害時はfallbackへ記録し、DB再試行を1分以上間隔に制限する。
- 設定読み込みを起動時の診断例外処理に含める。設定が復旧不能なら空設定で黙って起動しない。
- ストレージの保存先、時刻、プロセス操作、イベント出力をテスト用に注入可能にする。

## 6. 診断ZIPから対応する秘密引数を除去する

- 共通マスキングを新規イベント記録と診断出力に適用する。
- 対応名は`password`、`passwd`、`token`、`api-key`、`api_key`、`secret`。空白、`=`、引用符付き値を扱う。
- 設定、構造化JSONの文字列、診断用fallbackログを処理する。
- 過去DBに平文が残る前提で、一貫した読み取り結果から新しいマスク済みDBを作る。
- 生DBのコピーや、コピー後のUPDATEだけで済ませない。読み取り失敗時も生ファイルへフォールバックしない。
- 取得不能項目は`collection-notes.txt`へ記録する。元の設定・DB・過去ログは変更しない。
- 任意形式の秘密情報を完全に除去できるとは説明しない。

## 7. 長期稼働時のログ容量を管理する

- 起動後と1時間ごとに保持期限を超えたイベントを削除する。
- DB単位のプロセス間ロックと成功時刻で、両ホストによる重複整理を避ける。
- 容量目標は`EventDatabaseMaxMegabytes`、既定100 MiB、最小10 MiB。
- 超過時は古いイベントをバッチ削除し、使用ページ容量を目標の90%以下へ整理する。
- checkpoint／VACUUMは容量超過時だけ実施する。ロック競合時は短時間で中断し、次回へ回す。
- 容量目標は瞬間的な厳密上限ではない。WAL、一時超過、物理縮小延期を文書化する。
- fallbackは5 MiBで回転し、現在分＋旧2世代を保持する。書込と回転を同じ排他で保護する。

## 8. 検証と完了条件

| 分類 | 必須確認 |
| --- | --- |
| 差分再読み込み | Stop、Pause期限、Backoff、履歴、追跡PIDが保持される |
| タイマー | 自動解除が完了し、古いタイマーが新しい設定を解除しない |
| 停止意図 | Resume、再読み込み、復旧待機満了で勝手に起動しない |
| 競合 | Stop／再起動、旧終了イベント、破棄の競合で余分な起動や未処理例外がない |
| ホスト連携 | 両側成功、片側失敗、未使用Helper不在を区別する |
| 設定 | 独立2プロセスの初回作成・移行・保存で破損・更新消失がない |
| DB障害 | 初期化、書込、整理の失敗でも監視を継続する |
| 診断 | ZIP全ファイルのバイト検索でダミー秘密値が見つからず、元DBは不変 |
| 容量 | 保持期限、上限、整理競合、fallback回転を隔離データで確認する |
| 配布 | 両ZIPにテストランナー、テストDLL、補助テストプロセス、ユーザーデータを含めない |
